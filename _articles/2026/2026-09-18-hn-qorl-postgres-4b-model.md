## 原文概要

Rohan Bansal 在博客 [Training a 4B model to produce 81% faster query plans than Postgres](https://rohanbansal.com/qorl)（hn_id 49731285，662 分）里做了一个看起来矛盾但具体可复现的实验：把一个 4B 规模的开放权重模型用 SFT（监督微调）+ agentic RL（智能体强化学习）专门训练成 Postgres 的查询计划生成器，让它生成的执行计划比 Postgres 自带优化器快。

实验背景：4B 模型一开始对 99 条 join-heavy 查询生成不了任何计划。训练结束后，在 113 条 join-heavy 查询上拿到 1.81x geometric mean 速度提升，整体延迟平均下降 44.7%。整个实验烧的资源是租 Lambda 的 2x H100 SXM 节点 ~95 小时（约 800 美元），加上调用 OpenAI API 生成 500 条 GPT-6 Astra 智能体轨迹（约 400 美元）。

具体技术上，作者做了几件不太常见的事——给 Postgres 搭了一个测量装置降低 Linux page cache 在并发容器间的噪声；为 RL rollout 设计了一个 GRPO 的变体来处理环境噪声；RL 训练跨两台机器跑（vLLM + trainer 在租的 2x H100 节点上，4 个 Postgres 容器在自己的桌上）。

文章还科普了一个事实——一个 3 表 join 的 IMDb 查询，Postgres 内部其实有 4,608 种不同的执行方式（2 个 join 树 × 22 个内外顺序 × 32 个算法 × 43 个 scan），默认优化器用动态规划（外加 GEQO 遗传算法处理 12 表以上查询）做剪枝。

I would be cautious about over fitting, it's tough to say if those query plans would really be more optimal than Postgres heuristics at scale and with a bit more realistic OLTP workloads." — refibrillator [c:49733010]

> （译文：「比 Postgres 快 81%」——但测试集是 8GB、能全部塞进内存的 dataset，shared_buffers 还被限制到更小，query 是测前 warmed 过的，而且全是只读 SELECT。我对过拟合有点警觉，这些 query plan 是不是真的比启发式优，要在 OLTP 这种偏真实的工作负载里跑过才能下结论。）

### Cost estimation：Postgres 优化器的真正难题

中间有人提出「Cost Based Optimization」是优化器的本质：

> "You create formulas to estimate the cost of running a given query plan. Use statistics collected about the tables (e.g. how many rows) to try to be accurate. The topic is 'Cost Based Optimization'." — haroldl [c:49734906]
>
> （译文：写公式估算给定查询计划的代价，用表上收集的统计（比如行数）尽量估准。这一行的名字叫「基于代价的优化」（Cost Based Optimization）。）

Sesse__（看起来是 Postgres 圈内人）从根上反驳了 LLM 的必要性：

> "If you have formulas that actually match reality, what do you need the LLM for? An optimizer is perfectly capable of finding the optimal plan if it has a perfect estimator. In fact, if you could only estimate the number of rows in each subplan perfectly, you have as good as solved the problem already." — Sesse__ [c:49737060]
>
> （译文：如果你有真能匹配现实的代价公式，你还需要 LLM 干嘛？如果能完美估算每个子计划的行数，问题就算解决了，优化器本来就能找到最优计划。）

而 malisper 的回应把这点拉回了更悲观的现实：

> "Even if the query plan was not generated by an llm, you can't verify it will run in an acceptable time. This is one of the biggest unsolved problems in databases" — malisper [c:49741815]
>
> （译文：哪怕 query plan 不是 LLM 生成的，你也没法验证它跑起来时间够短。这是数据库里最大的未解问题之一。）

## 总体情绪

整体偏怀疑，但不是优化派，部分激进。

技术派普遍同意一个判断——优化器是难题，但 LLM 不是这个难题的对工具。4B 模型能做到的事情更像是一个特定的 RL 微调配方碰巧在 IMDb 这种特定数据集上撞到了局部最优，没人相信它能直接复制到 OLTP 场景里。但没人真的在技术上否认实验本身的真实性——数字是诚实的，方法也是诚实的，问题出在「测试集能不能代表真实生产」。

工程派的情绪最务实也最尖刻。生产环境对查询计划有两个核心要求——可调试、可验证。一个 LLM 生成的计划，出了事你没法复现，没法定位，更没法快速修。这种「黑盒上生产」在数据库这种关键基础设施上是不能接受的。

最有意思的暗线是 distillation 的伦理讨论。Astra 智能体轨迹来自 OpenAI GPT-6，小模型蒸馏这件事放在一年前是禁忌，现在变成公理——所有人都默认小模型在做蒸馏。争论的已经不是「该不该做」，而是「大模型自己数据来源是不是干净」。

最后一句话大概是——这是一个诚实的实验，但不是一个智能体评估「数据库优化器需不需要被 LLM 替代」的标准答案。Postgres 优化器几十年来没解决的问题，不是 4B 模型加 95 小时 H100 能解决的。
