## 原文概要

OpenCode 2.0 是来自 anomaly.co 的 TUI 编码 agent 的一次大重构。官方 blog 把它描述成"汲取数百万日活用户经验后的系统级改造"，重点是把客户端/服务端模型从"高级用户彩蛋"提升为默认后台常驻进程——TUI、Web、桌面 app 全部连接到同一个本地 service，CLI 也新增 `opencode api` 子命令，可以跨主机暴露供 `/pair` 命令连接。

API 被完全重写，团队称"旧版本是野蛮生长，新版本是看完所有奇怪场景后从零设计的"。官方还配套发布 `@opencode/client`（vanilla JS + Effect 两个客户端），新服务能感知自己的 API，例如能在启动新任务时把当前 session 自动挪进 git worktree。

2.0 新增的功能密度不低：`Code Mode` 在 `@opencode/codemode` 包内置一个最小 JavaScript 解释器，能把 MCP server 和 OpenAPI endpoint 转换成函数供 agent 在脚本中拼接调用，避免逐次往返；后台子代理允许主 agent 异步起一个用不同模型的子任务做"评审"；shell 命令也支持异步。插件系统被强制改造：所有 2.0 功能先以内部插件形式实现，数量在 80 个以上。`@opencode/sdk` 则让 OpenCode 可以作为库被其他 runtime 嵌入到 Durable Objects 等环境里。升级路径是 `opencode upgrade --major`，但官方明确警告三个破坏性变更：1.0 插件不再可用、server API 完全不同、`tui.json` 改名 `json`。

## 讨论焦点

### 后台常驻绕过了沙箱

将所有工具调用集中到后台进程是这次改动的支柱级决策，但它把"绕开 TUI 直接发起的工具调用"这条防线也顺手拆了。

> "it feels like a clear improvement across the board but a heads up: i got bitten by upgrading - since all tool calls now go through the background process, the sandbox that i use to wrap the TUI process quietly became useless. took me a day or two to realize that web fetches, etc. which should have been blocked were succeeding." — kingds [c:50095629]

> （译文：整体看是明显的进步，但提醒一下：升级后我被坑了——所有工具调用都走后台进程之后，我用来包 TUI 进程的沙箱静悄悄失效了。一两天后我才反应过来，本该被拦掉的网页拉取在悄悄成功。）

这是少数用户第一时间就意识到的问题——沙箱包的是进程边界，而 v2 把边界从 TUI 搬到了 service。一旦接受后台服务是常态，环境隔离的模型就需要重新设计，单靠"在 TUI 外层套个 bash sandbox"已经不够。

### 三到四处安全回归的具体清单

[`verdverm`](https://news.ycombinator.com/item?id=50096879) 在 24 小时内把这一波新回归归纳成了可数的几条：

> "There are at least 3 security regressions (imo) in the initial v2 release<br>1. configuration loading (now fixed) dropped support for system level, then restored it incorrectly, now it is better, but still some issues in user space<br>2. hot-reloading of plugins, agents can now change them with immediate effect<br>3. this, which I was unaware of<br>I wonder how many more there are given this much has been found already" — verdverm [c:50096879]

> （译文：v2 初始版本至少有 3 处安全回归（个人观点）：1. 配置加载（现已修复）丢了系统级支持，后续恢复得不彻底，用户态还有问题；2. 插件的热重载，agent 现在能即时改动它们；3. 上面那条，我之前没意识到。已经被挖出这么多，难以想象还有多少没被发现的。）

[`Cannabat`](https://news.ycombinator.com/item?id=50098285) 当晚又给清单加了第 4 条：

> "4. Tools added by plugins don't respect your permission config! For example you can set a tool to always ask when used, but it auto allows." — Cannabat [c:50098285]

> （译文：第 4 条——插件新增的工具不尊重你的 permission 配置！比如你可以设定某个工具使用前必须询问，结果它直接放行。）

把这两条放在一起看，问题已经不再是"bug 修修就好"：配置加载、插件热重载、permission 三条相互独立的路径都在一次大改里被同时打洞。verdverm 自己也承认花了整整一周帮对方理解 config loading 那条回归，最后靠两个 issue/PR 才推过去。"vibecoded" 的批评声越来越多，而官方并未对这些攻击面做出整体回应。

### 官网与安装器：trace 接口造的假进度条

如果说安全回归是用户主动去挖的，那官网性能是被动躺枪的：

> "And they created the slowest webpage on the planet Earth. Full throttle slop." — lofaszvanitt [c:50097060]

> （译文：他们做出了地球上最慢的网页。油门踩到底的 slop。）

配套佐证是一长串机型报告：M3 Pro 打开有可感卡顿、Pixel 6 几乎不能滚动、Pixel 11 也一样、M4 Pro 的风扇被叫醒。罪魁并非渲染管线自身，而是被反向工程出来的 [安装器进度条](https://github.com/anomalyco/opencode/issues/22998)：

> "I think it's due to they are doing a funny business to parse the progress, that's pretty much vibed and no one care. Like instead of using curl's progress, they re-invented a progress tracking with the tracing interface (--trace-ascii), byte by byte :(" — mayli [c:50096865]

> （译文：我觉得是因为他们用了一种骚操作来解析进度，基本是 vibe 出来的，没人关心。不是用 curl 自己的进度，而是用 tracing 接口（--trace-ascii）一个字节一个字节地造了一个进度条。）

[`denysvitali`](https://news.ycombinator.com/item?id=50095874) 给出了第一手测量：进度条走到 10% 用了 6 分钟，绕开办法是把 stdout 重定向给 `cat`。[`tjwebbnorfolk`](https://news.ycombinator.com/item?id=50097250) 在另一台机器上跑出来 24.975s 总时间——指向同一段代码在重定向场景下速度可观。两组数据的差值几乎可以反推"渲染性能"在 v2 安装器里反客为主成了延迟的主要来源。上游随后以 [commit d099d2c](https://github.com/anomalyco/opencode/commit/d099d2cb2a0869d07d2f533c66348e4868325a78) 和 [PR #55586](https://github.com/anomalyco/opencode/pull/55586) 修掉了这处具体行为。

附带议题是剪贴板劫持：

> "and they probably haven't stopped hijacking copy paste." — cyanydeez [c:50097343]
>
> "you are correct, still hijacking" — verdverm [c:50098799]

> （译文：他们大概还没停止劫持剪贴板。——你说得对，还在劫持。）

这对一条 TUI 来说是 comp-grade 的可用性问题，决定相当一批"不愿意被复制时被拦截"的用户宁愿只跑 web 客户端或 OpenChamber。

### 品牌混淆与社区控诉

2.0 发布贴下被反复追问的不只是功能，还有项目来历：

> "Wait, but OpenCode got renamed to Crush and the original dev went on to that new project. Where did this come from? Is this a fork? Who is behind it?" — unrented7977 [c:50095558]

> （译文：等等，但 OpenCode 不是改名成 Crush，原作者也去了那个新项目吗？这是从哪儿冒出来的？是 fork 吗？谁在维护？）

[`chrysoprace`](https://news.ycombinator.com/item?id=50095909) 与 [`kzsh`](https://news.ycombinator.com/item?id=50095952) 互相补充事实：OpenCode 来自 anomaly.co（同 sst.dev 团队），原仓库有维护者去了 Charm 开新项目 Crush，但 OpenCode 本身作为 TypeScript 重写一直在继续。这条回贴收到了 [`jauntywundrkind`](https://news.ycombinator.com/item?id=50097620) 的疲惫回应：

> "I'm really tired of this being retread time and time and time again.<br><br>It's just not interesting, it doesn't seem to matter, they are are separate projects and both doing great. The inside baseball about old history doesn't feel like it goes anywhere, adds anything. It didn't the last 5 times opencode got submitted!" — jauntywundrkind [c:50097620]

> （译文：我真的累了，这个问题被反反复复拿出来嚼。它既不有趣，也没啥影响，两个项目分开运营而且都做得不错。关于旧史的内部八卦让人走不到哪儿去，也加不了什么。前 5 次 OpenCode 上首页都是这样！）

积怨更直接来自 [`0xbadcafebee`](https://news.ycombinator.com/item?id=50095782) 的长篇控诉：

> "Same OpenCode team who ignore bug reports, don't respond on their discord, don't have modern CI/CD test suites (often shipping regressions), don't have bots to triage bug reports or PRs, and have what might be the worst open model subscription service available today.<br><br>OpenCode users: switching to Pi takes about 5 minutes, and customizing it to work just like OpenCode takes another 30 minutes. Better design, better devs, better community." — 0xbadcafebee [c:50095782]

> （译文：同一个 OpenCode 团队——无视 bug 报告、Discord 上不回话、没现代化的 CI/CD 测试套件（经常带着回归发版）、没有机器人分流 issue 和 PR、还做着可能是市面上最烂的开源模型订阅服务。OpenCode 用户：切换到 Pi 大概 5 分钟，再花 30 分钟把它定制成 OpenCode 的样子。更好的设计、更好的开发者、更好的社区。）

这条回贴正撞上 [`verdverm`](https://news.ycombinator.com/item?id=50097037) 自述"刚从 OpenCode 转到 Pi"的同款意见——bug 报告没人理、回归直接发版——叠加到 2.0 发布当天的安全回归清单上，看起来不是孤立情绪。

### 后台子代理与 Code Mode：少数被一致认可的改动

在同一波批评声中，后台子代理这条改动几乎没收到反对票：

> "The background task / subagent feature and the ability to specify a model when starting a subagent are so far my favorite improvements. Small things but make huge QoL difference in everyday development." — 361994752 [c:50095652]

> （译文：后台任务 / 子代理，以及在起子代理时可以指定模型——这两个是我目前最喜欢的改进。小改动，但日常开发体感差别巨大。）

[`afruitpie`](https://news.ycombinator.com/item?id=50095797) 则把眼光放在"本机开 server、远端连上来跑 session"的形态上，指出 Claude Code 当前在 desktop app 重连时清空 session 的设计很尴尬，希望看到 Anthropic 学习类似模型。同一讨论里 [`awkii`](https://news.ycombinator.com/item?id=50098630) 自述做过类似的多 harness 代理器，包括读取未公开但稳定的 VSCode 插件 ↔ Claude Code 本地 API。

Code Mode 的好处被简化为"加一千个 MCP 也不会爆 context，agent 自己组合"，潜在风险是 `Code Mode` 解释器让 agent 写脚本的"自由度"显著大于"单次调用"，跟上面 permission regression 叠加，会让"agent 写一段绕过鉴权的 JS"变得在技术上毫无阻碍。

### 订阅服务对决：OpenCode Go vs Charm Hyper

最后被反复推上台面的是价格卡位战。OpenCode Go 的 [$10/月配额](https://news.ycombinator.com/item?id=50097106) 被 [`0xbadcafebee`](https://news.ycombinator.com/item?id=50097691) 用 [Charm Hyper](https://hyper.charm.land/) 反驳：

> "Charm Hyper is not only a better deal ($350 of credit on all models for $20), but their models don't run at 20t/s, more like 200t/s" — 0xbadcafebee [c:50097691]

> （译文：Charm Hyper 不仅是更划算的交易（$20 给 $350 credit 跑所有模型），他们的模型不是在 20t/s 上跑，更像 200t/s。）

[`verdverm`](https://news.ycombinator.com/item?id=50098184) 反驳回去，称 Hyper 的文档稀少、定价用 credit 抽象：

> "I'm not interested in credit abstractions and no amount of convincing will change that, same reason I have no interest in Circle CI" — verdverm [c:50099676]

> （译文：credit 这种抽象引不起我的兴趣，无论如何推都不会改变，跟我没兴趣用 Circle CI 是同一个理由。）

[`0xbadcafebee`](https://news.ycombinator.com/item?id=50099326) 在下一条贴里把等价算出 $12.50/天（250 credits × $0.05）并列出 Hyper 已经上架的 Qwen / DeepSeek / Moonshot / Z.AI / MiniMax / gpt-oss-120b / gemma-4-26b 模型组合。这条讨论完整地呈现了"开源编码 agent"赛道当前以**月费 + 模型聚合**作主战场的事实。

## 总体情绪

讨论从最初几小时的功能展示滑向了治理与信任问题——后台进程吃掉沙箱边界之后，热重载和 permission 又各自开了独立的口子；同期被点名的"地球上最慢网页"和 trace 接口造的进度条，则把性能层面的粗糙一起搬到聚光灯下。少数被一致认可的两处改动（后台子代理、Code Mode、SDK）反而是更深层的杠杆：它们让 agent 写脚本/agent 写 plugin/agent 跑远端 session 成为可能，而这些能力与上述三组回归叠加，意味着 OpenCode 2.0 在"开发者主动想要的功能"和"被动暴露的攻击面"两端同时膨胀。

> vibe 出来的 vibe coding 工具，最怕的是冒出 vibe 出来的 bug——而这次冒出的位置，刚好在沙箱边界上。
